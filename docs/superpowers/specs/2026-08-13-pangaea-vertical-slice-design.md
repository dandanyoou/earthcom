# PANGAEA 데모 수직 슬라이스 설계

작성일: 2026-08-13  
상태: 승인됨  
정본: `PANGAEA_통합_개발명세서_v1.0.md`, `PANGAEA_데모_수정.html`

## 1. 목적과 범위

PANGAEA는 인증된 개인과 팀을 미리 등록하고, 필요한 사람이 생겼을 때 국경과 상관없이 조건에 맞는 참여자를 찾고 협업까지 이어 주는 서비스다. 이번 구현은 가입부터 프로필, 시그널, 추천·검색, 지원·초대, 협업, 보증금 sandbox, 다국어 채팅, 완료·평가, 신뢰 온도 갱신까지 하나의 실제 동작하는 수직 슬라이스로 연결한다.

구현 범위는 통합 명세서의 T-01부터 T-50까지다. 운영자 UI, 실제 결제, 과실 귀속 활성화, 소셜 로그인, 푸시 알림, 신조어 승격 UI는 만들지 않는다. 해당 영역은 명세가 요구하는 포트·API·권한 검사 또는 비활성 상태만 유지한다.

## 2. 선택한 접근

명세의 태스크 순서를 그대로 따르는 단일 모노레포 방식을 사용한다. 프론트 데모를 먼저 만들거나 백엔드를 먼저 완성하는 방식은 빠른 부분 결과를 만들 수 있지만, 화면·API·상태 머신·AI 경계가 서로 다른 시점에 굳어질 위험이 있다. PANGAEA의 핵심은 AI가 표현하고 결정적 코드가 판정한다는 경계이므로, 기반부터 최종 E2E까지 계약을 함께 세우는 순차 구현이 가장 안전하다.

각 태스크는 다음 순환을 따른다.

1. 태스크의 계약과 실패 테스트를 먼저 추가한다.
2. 최소 구현으로 테스트를 통과시킨다.
3. 관련 정적 검사와 통합 검사를 실행한다.
4. 변경을 스테이징하고 파일 목록을 확인한다.
5. 한 태스크 단위로 커밋하고 `docs/PROGRESS.md`에 결과를 남긴다.

## 3. 시스템 구조

저장소는 네 영역으로 나뉜다.

- `frontend/`: Next.js 15 App Router, TypeScript, Tailwind CSS v4, next-intl 기반 웹 앱
- `backend/`: FastAPI, SQLAlchemy 2, Pydantic v2, Alembic 기반 모듈러 모놀리스
- `ai/pangaea_ai/`: 백엔드 프로세스 안에서 실행되는 AI 표현 계층
- 인프라: PostgreSQL 16과 pgvector, Redis 7, MinIO, Docker Compose

프론트는 생성된 OpenAPI 클라이언트만 사용한다. 백엔드는 인증, 프로필, 시그널, 탐색, 지원, 협업, 채팅, 보증금, 신뢰 도메인을 독립된 모듈로 유지하고 명시적인 서비스 인터페이스로 연결한다. AI 패키지는 별도 네트워크 서비스가 아니며 백엔드 통합 포트를 통해서만 호출된다.

## 4. 프론트엔드 설계

모바일 화면을 정본으로 삼고 페이지 컴포넌트는 폼팩터를 알지 못하게 한다. `AppShell`만 브레이크포인트에 따라 모바일 하단 탭과 데스크톱 좌측 내비를 전환한다. 1440px 이상의 채팅 화면에서는 같은 메시지·문화 도우미 컴포넌트를 3단 셸에 배치한다.

색상, 간격, 타이포, 카드, 칩, 버튼, 행, 접힘 패널은 HTML 데모의 토큰과 위계를 이식한다. 폰 베젤과 가짜 상태바는 `/demo`에서만 사용한다. 실제 앱의 모든 버튼과 링크는 통합 명세서 §3.2의 도착 화면 또는 상태 변화에 연결한다.

UI 문자열은 `messages/ko.json`과 `messages/en.json`에만 둔다. 두 파일은 키 집합이 같아야 하고 JSX의 한글 리터럴은 ESLint로 차단한다. UI 언어와 채팅 번역 대상 언어는 서로 다른 상태로 관리한다.

## 5. 백엔드와 데이터 설계

FastAPI 애플리케이션은 API, 도메인, 통합, 정책, 플랫폼 계층으로 나눈다. 도메인 상태 전이는 서비스 계층과 데이터베이스 제약으로 함께 보호한다. 모든 mutation은 멱등성 키와 버전 충돌을 검증한다. 지원 수락 시 협업, 멤버, 기본 대화 생성은 하나의 트랜잭션으로 처리한다.

보증금은 WORK와 BOOKING에만 적용한다. sandbox provider가 예치와 환급 이벤트를 만들고, 원장은 통화별 균형과 provider 이벤트 중복 방지를 강제한다. 작업 대금, 정산, 지분, 비율 필드는 어떤 API나 테이블에도 만들지 않는다.

신뢰 온도는 `trust_events`만 입력으로 사용하는 `trust.v1` 결정적 projection이다. 채팅 가드 무시 이력은 감사 로그에만 남고 신뢰 이벤트를 만들 수 없다. 정책을 비활성화하면 API는 정상 응답과 `UNAVAILABLE` 상태를 반환한다.

## 6. AI 경계

AI는 자연어 구조화, 번역, 문화 주석, 발신 전 경고, 추천 이유 문장, 보증금 조건 문구, 검색어 정규화만 담당한다. 역할 설계, 순위, 점수, 신뢰 온도, 보증금 금액, 과실 판단은 담당하지 않는다.

이 경계는 네 단계로 강제한다.

1. 판단 수치를 AI 입력에 전달하지 않고 슬롯 이름만 전달한다.
2. strict Pydantic 스키마에서 판단 필드를 표현할 수 없게 한다.
3. 근거·고정관념·숫자·슬롯·번역 게이트를 발행 전에 적용한다.
4. 하드 실패 스캐너와 계약 테스트가 위반 경로를 CI에서 차단한다.

AI 실행 모드는 `live`, `replay`, `stub` 세 가지다. API 키가 없으면 stub으로 모든 화면과 테스트가 동작한다. 스키마를 위반하거나 게이트를 통과하지 못한 모델 결과는 폐기하고 결정적 폴백을 사용한다. 근거가 없는 문화 주석은 폴백 문장으로 채우지 않고 렌더하지 않는다.

## 7. 주요 데이터 흐름

1. 사용자가 가입하고 개인 또는 팀 프로필, 스킬, 언어, 가능 시간을 등록한다.
2. 사용자가 시그널 본문과 필요한 역할을 직접 입력한다.
3. AI 파서가 본문을 구조화하되 역할 multiset은 사용자 폼과 정확히 같아야 한다.
4. 사용자가 추정값을 확인한 뒤 결정적 발행 게이트를 통과하면 시그널이 열린다.
5. 서버 정책이 hard filter와 사전식 정렬로 추천·검색 결과를 만든다. AI는 결과 순서에 관여하지 않고 이유 문장만 만든다.
6. 지원 또는 초대를 수락하면 협업과 대화가 생성된다. WORK·BOOKING은 보증금 합의 후 활성화되고 HELP·CIRCLE은 바로 대화로 이동한다.
7. 발신 전 가드는 경고만 제공한다. 사용자가 그대로 보내기를 선택해도 메시지는 전달된다.
8. 번역 실패나 숫자 불일치가 있으면 원문을 병기한다. 근거가 있는 경우에만 문화 주석을 비동기로 붙인다.
9. 완료 확인 후 sandbox 환급, 상호 평가, `trust_events` 추가, 신뢰 온도 재계산, 크루 해산이 순서대로 수행된다.

## 8. 오류·보안·복구

API는 일관된 응답 봉투와 제품 오류 코드를 사용한다. 409와 422 오류는 프론트에서 해당 폼이나 액션 근처에 표시한다. DB, Redis, 마이그레이션 불일치는 readiness 실패로 나타내며 live 상태와 구분한다.

인증은 Argon2id 비밀번호, 15분 access token, 30일 refresh token 회전과 재사용 탐지를 사용한다. 모든 객체 접근은 `acting_profile_id` 권한 컨텍스트를 거친다. 업로드는 격리 상태에서 공개·AI 전달이 차단된다. 로그와 fixture에는 원문 PII, 토큰, 메시지를 남기지 않는다. OpenAI 키는 백엔드 런타임에만 존재하며 프론트 번들과 저장소 검사가 이를 강제한다.

WebSocket 연결이 끊기면 커서 기반 재연결로 누락 이벤트를 복구한다. 외부 효과는 outbox와 멱등성 키로 중복 실행을 막는다.

## 9. 테스트와 완료 판정

태스크마다 단위, 저장소, 계약, 통합, 보안 테스트 중 필요한 층을 추가한다. Playwright는 모바일·데스크톱과 ko·en의 네 조합에서 핵심 흐름과 모든 인터랙션을 검증한다. AI 평가는 30문항 중 27문항 이상을 통과해야 한다. 명세의 하드 실패 조건 21종은 CI에서 하나라도 발견되면 실패한다.

전체 구현 후 세 검수 역할을 같은 라운드에서 실행한다.

- 본질 검수: 명세 누락, 범위 확장, AI 판단 유입 확인
- 동작 검수: 모든 화면과 버튼, B01~B16, 실패 경로 확인
- 디자인 검수: 6개 폭과 2개 언어에서 겹침, 잘림, 대비, 목업 회귀 확인

세 리포트가 같은 라운드에서 모두 PASS해야 완료로 판정한다.

## 10. 작업 지속성과 인계

`docs/PROGRESS.md`에는 완료 태스크, 날짜, 커밋, 테스트 결과를 남긴다. `docs/DECISIONS.md`에는 명세에 없는 구현상 가정과 근거를 남긴다. 각 세션은 PROGRESS의 마지막 완료 태스크 다음부터 재개한다.

대화 문맥 사용량이 약 50%에 도달하면 현재 태스크의 안전한 중단 지점까지 마치고 다음을 포함한 재개용 프롬프트를 작성한다.

- 저장소와 작업 브랜치 또는 worktree 경로
- 마지막 완료 태스크와 커밋
- 실행한 테스트와 결과
- 변경 중인 파일과 미완료 사항
- 다음 태스크의 정확한 시작점
- 필요한 실행 명령과 주의할 불변 규칙

코드보다 `docs/PROGRESS.md`와 커밋을 정본으로 삼아 새 세션이 추측 없이 이어받게 한다.

## 11. 확정 결정

- 통합 명세서와 수정 HTML을 정본으로 사용한다.
- T-01부터 T-50까지 문서 순서대로 구현한다.
- 모바일·데스크톱과 ko·en을 처음부터 동일한 컴포넌트 계약으로 유지한다.
- 실제 결제와 외부 유료 API 키 발급은 수행하지 않는다.
- `main`에 직접 커밋하지 않는다.
- 명세에서 금지하거나 제외한 기능은 편의상 추가하지 않는다.
